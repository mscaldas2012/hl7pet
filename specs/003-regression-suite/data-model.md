# Data Model: Shared Regression Suite (`fixtures/` Corpus)

This spec produces a consolidated data corpus plus a small validation tool, not a
running application — "entities" here are the conceptual objects the corpus and its
tooling are built from, mirroring (and extending, not replacing) the entities already
defined in `specs/001-path-grammar-spec/data-model.md` and
`specs/002-hierarchy-semantics/data-model.md`.

## Entities

### Fixture Corpus

The single canonical directory tree at `fixtures/` (repo root).

| Field | Description |
|---|---|
| `messages_dir` | `fixtures/messages/` — every Golden Message, flat (no per-spec subfolders) |
| `profiles_dir` | `fixtures/profiles/` — every Profile JSON (currently only from spec `002`) |
| `vector_families` | `fixtures/vectors/<family>/` — one subdirectory per Vector Family (`path`, `hierarchy`, and any added by later specs) |
| `schemas_dir` | `fixtures/schemas/` — one JSON Schema file per Vector Family |
| `scripts_dir` | `fixtures/scripts/` — `validate_corpus.py` (FR-004/FR-005/FR-006) |

**Relationships**: contains many Golden Messages, Profiles, and Conformance Vectors
(grouped into Vector Families); validated as a whole by one Coverage Report.

**Validation rules**: every Conformance Vector's `message_ref`/`profile_ref` MUST
resolve to a file under this corpus's `messages_dir`/`profiles_dir` (FR-004.2); every
vector `id`, corpus-wide across all families, MUST be unique (FR-003, FR-004.3).

### Vector Family

A named group of Conformance Vectors sharing one JSON Schema and one coverage
dimension.

| Field | Description |
|---|---|
| `name` | Directory name under `fixtures/vectors/`, e.g. `path`, `hierarchy` |
| `schema_ref` | Which file under `fixtures/schemas/` this family's vectors validate against |
| `coverage_dimension` | Which field on each vector drives coverage counting: `grammar_productions` for `path`, `semantic_rules` for `hierarchy`, or `null` for an unrecognized family (FR-007) |
| `origin_spec` | Which spec introduced this family (`001` for `path`, `002` for `hierarchy`) |

**Relationships**: groups many Conformance Vectors; owns one schema file.

**Validation rules**: a family with `coverage_dimension: null` (an "unrecognized
family" per FR-007/Decision 4) MUST still be schema-validated and reference-checked
(FR-004.1/FR-004.2) — only coverage-report categorization is skipped, not validation.

### Conformance Vector

Identical in shape to the entities already fully specified in
`specs/001-path-grammar-spec/data-model.md` (`path` family) and
`specs/002-hierarchy-semantics/data-model.md` (`hierarchy` family) — this spec does
not redefine their fields, only where they live now:

| Family | Schema (now under `fixtures/schemas/`) | Vector files (now under `fixtures/vectors/<family>/`) |
|---|---|---|
| `path` | `conformance-vector.schema.json` | `path/valid.json` (11 records), `path/invalid.json` (6 records) |
| `hierarchy` | `hierarchy-conformance-vector.schema.json` | `hierarchy/basic.json` (4 records), `hierarchy/complex.json` (6 records) |

**Validation rules** (unchanged from origin specs, re-enforced here corpus-wide):
`id` unique across the *entire* corpus, not just its own family or file (FR-003 —
stricter than spec `001`/`002`'s own "unique within the suite" wording, which meant
their own single-family suite); every `message_ref`/`profile_ref` resolves; content
otherwise byte-identical to what specs `001`/`002` authored and Scala-verified
(FR-002).

### Golden Message

Identical entity to spec `001`'s "Synthetic HL7 Message," now living under
`fixtures/messages/` regardless of which spec originally authored it. No
`origin_spec` field is tracked on the message itself (unlike Vector Family) — a
message may end up referenced by vectors from multiple families/specs over time, so
attributing it to one origin would be misleading past this spec's initial
consolidation.

| Field | Description |
|---|---|
| `path` | File path under `fixtures/messages/` |
| `content` | Raw HL7 v2 text |

**Validation rules**: MUST NOT contain real patient data, even de-identified
(inherited from spec `001` FR-009 / spec `002` FR-012, re-stated as this spec's
FR-010).

### Profile

Identical entity to spec `002`'s profile fixtures (`segmentDefinition`-style JSON),
now living under `fixtures/profiles/`.

| Field | Description |
|---|---|
| `path` | File path under `fixtures/profiles/` |
| `content` | Declarative segment-definition JSON, per spec `002`'s hierarchy-semantics contract |

**Relationships**: referenced by zero or more `hierarchy`-family Conformance Vectors
via `profile_ref`.

### Coverage Report

A derived artifact (not committed — regenerated by `validate_corpus.py` on each run),
produced by FR-006/FR-007.

| Field | Description |
|---|---|
| `dimension` | Coverage dimension name, e.g. `grammar_productions`, `semantic_rules`, or an unrecognized-family bucket name |
| `covered` | Map of production/rule name → list of covering vector ids |
| `gaps` | List of production/rule names in the dimension's known enum with zero covering vectors |
| `unrecognized_families` | List of `{family, vector_count}` for families with `coverage_dimension: null` |

**Validation rules**: a run with any non-empty `gaps` list for the `path` or
`hierarchy` dimensions fails CI (SC-004 requires zero gaps for these two — both
source specs already required 100% coverage before being marked complete).
`unrecognized_families` entries never fail the run (FR-007) — they're informational,
surfaced so a later spec can decide whether to register a new coverage dimension.

**Lifecycle**: regenerated fresh on every `validate_corpus.py` invocation; has no
persisted state of its own between runs (no state-transition model, unlike
Conformance Vector's `Drafted → Verified` lifecycle in spec `001`, since this report
doesn't represent an in-progress authoring workflow — the vectors it reports on are
already `Verified` before entering this corpus, per FR-002).
